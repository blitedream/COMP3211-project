## 第 2 页 · 四类记录（A，45 秒）

> A note stores plain text. A task has a description and a deadline. An event has a description, a start time and an alarm time. A contact has a name, an address and a mobile number. Each record has an ID that stays the same when we edit it or load it from a file. The same commands work with all four types: create, update, search, print, delete, save and load. For example, we can update a task deadline without changing its description.

## 第 4 页 · 需求 2：定义搜索条件（B，35 秒）

> Search conditions can check the record type, look for text in a field, or compare a time with a given date and time. We combine conditions using and, or and not. Not is evaluated first, then and, then or; parentheses change the grouping. In this example, the parentheses select tasks or events. The description must also contain report. A task or event without that word will not match.

**提示**

- 按 TYPE / TEXT / TIME 三行依次指。
- 讲到底部表达式时，手势比一下括号：“括号先算”。
- 不要把 `&&`、`||` 念成符号，说 and / or / not，听感更好。
- 不要深入 tokenizer 或解析实现，那是设计文档的事。

## 第 6 页 · 设计：架构（C，40 秒）

> Our design is MVC-inspired. PIMCli handles commands, with ConsoleView formatting the terminal; PIMModel owns records and delegates search. The CLI calls PIMFileCodec directly, and AtomicFileWriter stages and replaces saved files. These boundaries let us test domain rules without terminal input. Immutable replacements prevent partial updates, while ordered storage makes results predictable. Linear search is sufficient for this project scope; an index would add maintenance complexity. The trade-off is extra allocation and temporary disk space.

**提示**

- 顺箭头走一遍：Terminal → PIMCli → PIMModel，再向下指 Codec 和 Search。
- 强调 **model 不依赖 terminal**，这是能单测的原因，也是设计文档里的核心理由。
- 不要把 MVC 说成“三个独立的 Java 包”——我们是一个 CLI 适配器 + 一个 model 包。

## 第 7 页 · 设计：记录模型（D，35 秒）

> I am [D], and this is my student ID. All four record types extend an abstract PIR class and are immutable. An update builds and validates a replacement with the same ID, and commits it only if it is valid, so a rejected update cannot leave a half-changed record. The collection keeps insertion order, and the .pim file stores one block per record, with Base64 text fields and yyyy-MM-dd HH:mm timestamps.

**提示**

- 先亮学生证。
- 指类图：PIR 在上，四个子类在下，一句带过继承关系。
- 核心是 **same ID + validate before commit**，用手比“先验证、后提交”。
- 不要逐个念 getter / 字段，讲设计意图而不是 API 清单。

## 第 8 页 · 经验教训 + 收尾（D，40 秒）

> Our main testing lesson concerns failed saves. An error message does not tell us whether the old file survived. In this test, we start with an existing file and interrupt the staged write. We then compare the original bytes and check that the temporary file has been removed. These checks test the promise that a failed save preserves the previous data. All 56 model tests pass in JUnit, and JaCoCo reports 99.30 percent line coverage. The assertions check the results behind that number. Thank you.

## 可能被问到的问题

1. **为什么用 UUID 而不是自增 ID？** 不需要维护计数器，碰撞概率很低；载入时仍检查重复 ID。界面提供 1、2、3 这样的会话编号，完整 UUID 保存在文件中；搜索和删除不会让编号错位。重启后用 list 查看编号。
2. **为什么使用 JUnit？** 模型测试使用 JUnit 4.13.2 的 @Test 和 JUnitCore 自动发现、执行并报告结果；失败时退出码非零。JUnit/Hamcrest 仅用于测试，应用运行时仍只依赖 Java 标准库。CLI 集成检查单独执行。
3. **为什么 .pim 里用 Base64？** 文本可能含换行、`=`、中文，Base64 后每行一个字段，解析不会断。
4. **99.30% 的覆盖率说明什么？** 56 项模型测试执行了 model 中的 428/431 行；CLI 和测试报告器不计入。返回值、文件内容和异常由断言检查。
5. **搜索会不会改数据？** 不会；搜索只读快照，测试里也对比了前后集合。
